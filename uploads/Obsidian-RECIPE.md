# Vault Template

قالب آماده‌ی «ویکی دانش پروژه» — همان سیستمی که در این پروژه (`/project/.noqte/wiki/`) استفاده می‌شود، به‌صورت عمومی برای هر پروژه‌ی دیگر.

## استفاده
1. پوشه‌ی `wiki/` این قالب را داخل پروژه‌ی جدید کپی کن (پیشنهاد: `docs/wiki/`).
2. محتوای `RECIPE.md` را به‌طور کامل کپی کن و در ابتدای فایل `CLAUDE.md` یا `AGENTS.md` همان پروژه (یا هر جای دیگری که system prompt پروژه را می‌سازد) پیست کن.
3. از سشن بعدی، ایجنت خودش طبق قوانین `RECIPE.md` صفحات `overview.md` و `index.md` را می‌خواند، و بعد از هر تغییر معنایی در کد، ویکی را به‌روز نگه می‌دارد.

## محتوای این قالب
- `RECIPE.md` — متنی که باید کپی/پیست شود (دستورالعمل کامل برای ایجنت).
- `wiki/schema.md` — قوانین کامل ساختار و لینک‌گذاری (خودِ ایجنت بعداً آن را برای هر پروژه دقیق‌تر می‌کند).
- `wiki/overview.md`, `wiki/index.md`, `wiki/log.md` — اسکلت خالی با placeholder.
- `wiki/entities/`, `wiki/concepts/`, `wiki/sources/` — پوشه‌های خالی آماده برای صفحات آینده.

# Vault Recipe — دستورالعمل ویکی دانش پروژه

> این فایل را در ریشه‌ی هر پروژه‌ی جدید کپی کن (مثلاً به‌عنوان `CLAUDE.md`، `AGENTS.md` یا داخل system prompt).
> از این نقطه به بعد، ایجنت خودش پوشه‌ی `docs/wiki/` را می‌سازد و طبق این قوانین نگه می‌دارد.

## این چیست
یک «ویکی دانش» زنده و append-friendly کنار کد، که به‌جای re-scan کردن کل کدبیس در هر مکالمه،
خلاصه‌ی entity ها (مدل‌ها، سرویس‌ها، صفحات) و concept ها (flowها، الگوها، تصمیم‌ها) را نگه می‌دارد.
مسیر پیش‌فرض: `docs/wiki/` (اگر پروژه ساختار دیگری دارد، همان‌جا بساز و همین قواعد را اعمال کن).

## ساختار پوشه
```
docs/wiki/
  schema.md      # این فایل قوانین را نگه می‌دارد — خودت می‌نویسی و به‌روزش می‌کنی
  overview.md    # یک‌نگاه کلی پروژه (≤۴۰۰ کلمه)
  index.md       # کاتالوگ همه صفحات، گروه‌بندی‌شده، با خلاصه یک‌خطی
  log.md         # تاریخچه append-only (جدیدترین در پایین یا بالا — فقط یک‌جور انتخاب کن و ثابت بمان)
  entities/      # هر entity مهم یک صفحه (مدل دیتا، service، router، صفحه کلیدی UI)
  concepts/      # patternها، flowها، قراردادها، تصمیم‌های معماری
  sources/       # (اختیاری) خلاصه فایل‌های خام کدی که چندجا ارجاع داده می‌شوند
```

## شروع هر مکالمه/سشن
1. اول `overview.md` و `index.md` را بخوان (هزینه: ≤۸۰۰ توکن). هرگز کل کدبیس را re-scan نکن.
2. فقط صفحات مرتبط با تسک فعلی را drill-down کن (`entities/*.md`, `concepts/*.md`).
3. اگر `docs/wiki/` هنوز وجود ندارد، همین ساختار را با محتوای اولیه (overview کوتاه از روی README/package.json، index خالی، schema همین فایل) بساز.

## وقتی کد را تغییر دادی — قانون اکید
هر بار که یک فایل پروژه را Write/Edit می‌کنی (خارج از `docs/wiki/` خودش):
1. تشخیص بده این تغییر روی کدام entity/concept اثر می‌گذارد.
2. صفحه‌ی مربوطه را به‌روز کن (فیلد جدید/حذف‌شده، امضای تابع، route جدید، dependency جدید، edge case).
3. اگر entity/concept کاملاً جدید و به‌اندازه کافی مهم است (قانون زیر)، صفحه جدید بساز و در `index.md` لینک بده.
4. یک خط در `log.md` اضافه کن: `## [YYYY-MM-DD] update | <خلاصه تغییر>`.

تغییرات trivial (typo، فرمت، rename بدون تغییر امضا) نیاز به آپدیت ویکی ندارند.
اگر چند فایل در یک مکالمه تغییر کردند، آپدیت‌های ویکی را **یک‌بار در پایان مکالمه** انجام بده، نه بعد از هر فایل — برای کمترین رفت‌وبرگشت و سرعت بیشتر.

## چه وقت صفحه جدید بساز
- فقط اگر **≥۳ جای دیگر** قرار است به آن لینک بدهند، یا concept مستقلی با حجم قابل‌توجه است.
- در ۹۰٪ موارد به‌جای فایل جدید، **صفحه موجود را آپدیت کن** (یک paragraph یا section اضافه).
- هرگز صفحه‌ی trivial نساز (wrapper یک‌خطی، utility ساده) — در صفحه پدر یک bullet بنویس.

## ساختار صفحه‌ی entity
```markdown
# {نام}

> یک‌خطی توضیح هدف.

## مسئولیت‌ها
- ...

## وابستگی‌ها
- [[concepts/xxx]] — چرا
- [[entities/yyy]] — چطور

## قراردادها / Edge cases
- ...

## منابع کد
- `path/to/file.ts:42` — کلاس اصلی
```

## ساختار index.md
```markdown
# Index

## Overview
- [[overview]] — یک‌نگاه کلی

## Entities (X صفحه)
- [[entities/xxx]] — خلاصه یک‌خطی

## Concepts (Y صفحه)
- [[concepts/yyy]] — خلاصه یک‌خطی
```

## قواعد لینک (Obsidian-style)
- `[[entities/user]]` بدون پسوند `.md`.
- نام فایل: lowercase + hyphen (`auth-flow.md` نه `Auth Flow.md`).
- wikilinkهای نمونه داخل بک‌تیک/code block لینک واقعی محسوب نمی‌شوند.

## Lint دوره‌ای (وقتی کاربر گفت "ویکی رو بازبینی کن")
1. orphan pages (بدون inbound link) — لینک بده یا حذف کن.
2. broken link — صفحه‌ی گمشده را بساز یا لینک را حذف کن.
3. تناقض بین صفحات — flag کن، نپرس، بهترین حدس را انتخاب کن و در log ثبت کن.
4. صفحات کهنه (کد مرتبط تغییر کرده ولی صفحه آپدیت نشده) — بازخوانی و sync.

## نکته‌ی نهایی
اگر این قانون رعایت نشود، ویکی stale می‌شود و مکالمات بعدی به اطلاعات غلط می‌رسند.
هدف: کاهش توکن مصرفی با دانش فشرده و به‌روز — نه مستندسازی برای مستندسازی.
